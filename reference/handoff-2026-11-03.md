# 햇살병원 게임 프로젝트 — 전체 작업 인계서

이 문서를 바탕으로 이전 채팅에서 진행하던 게임 개발을 이어가 주세요.
기획만 다시 설명하고 끝내지 말고, 사용 가능한 작업 환경을 확인한 다음 실제 개발을 진행해 주세요.

1. 사용자와 협업 방식
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

사용자는 코딩 입문자이며, 모바일 게임 제작의 A부터 Z까지 도움을 원합니다.

- Android와 iOS 동시 출시가 목표입니다.
- 사용자는 아이디어, 분위기, 플레이 피드백을 제공합니다.
- AI가 기술 선택, 구현, 검증, 제작 계획 정리 등을 주도합니다.
- 진행 도중 새 아이디어를 계속 이야기할 수 있으며, 기존 목표에 반영해야 합니다.
- 이미 승인된 작업은 불필요하게 다시 허락받지 말고 진행합니다.
- 작업 중에는 무엇이 바뀌었는지, 무엇을 검증했는지 간단히 알려줍니다.
- 코딩을 모르는 사용자가 이해할 수 있도록 설명합니다.
- 생성 이미지, 디자인 시안, 실행되는 게임, 검증된 기능을 명확히 구분합니다.
- 실행하지 않은 코드나 확인하지 않은 기능을 완료했다고 표현하면 안 됩니다.
- 사용자가 보내준 기획용 HTML을 완성 게임의 화면 구조로 그대로 사용하면 안 됩니다.

사용자가 특히 싫어했던 이전 실수:
기획용 HTML 화면에 생성 이미지만 끼워 넣고 본게임 제작이 진행된 것처럼 보여준 일.
이후 실제 3D 공간과 별도 게임 프로젝트를 만드는 방향으로 수정했습니다.

사용자가 사용량 제한 후 자동 재개를 요청한 적이 있습니다.
하지만 이전 환경에는 사용량 리셋을 감지해 스스로 새 실행을 시작하는 기능이 없었습니다.
자동 재개를 예약했다고 주장하면 안 됩니다.
다음 메시지가 오면 저장된 인계 기록을 바탕으로 이어갑니다.

2. 프로젝트 이름과 핵심 방향
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

게임명: 햇살병원 방사선과
간단한 표시명: 햇살병원

핵심 장르:
따뜻한 분위기의 병원 운영·성장 게임.

사용자가 확정한 제작 방식:
“3D 공간이지만 카메라는 고정하고 운영에 집중”

따라서:
- 실제 3D 모델과 공간을 사용합니다.
- 고정된 비스듬한 시점으로 병원을 봅니다.
- 모바일 세로 화면을 우선합니다.
- 환자가 공간 안에서 실제로 이동합니다.
- 병원 운영, 장비 사용, 대기열, 직원 업무가 중심입니다.
- 카메라 자유 회전이나 자유 건축이 핵심 요구로 확정된 것은 아닙니다.
- 고정 카메라라는 이유로 큰 배경 이미지 한 장으로 대체하면 안 됩니다.

현재 사용 엔진:
Godot 4.6.3

새 환경에서도 설치 가능 여부와 프로젝트 호환성을 확인해야 합니다.

3. 아트 방향과 시안의 의미
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

사용자가 A, B, C 비교 시안 중 A와 C를 선호했고,
합친 A+C 시안을 본 뒤 좋다고 승인했습니다.

대화 기록에서 정리된 A+C 방향:
- 따뜻하고 친근한 병원.
- 귀여운 작은 비율의 캐릭터.
- 밝은 크림색, 청록색, 부드러운 코랄 계열.
- 식물과 햇살이 있는 편안한 분위기.
- 의료 장비는 어떤 장비인지 알아볼 수 있는 형태와 디테일.
- 귀여운 인물과 비교적 설득력 있는 병원 공간의 조합.

단, 정확한 이미지 원본이 새 채팅에 없다면
“기존 승인 이미지와 완전히 동일한 디자인”이라고 주장하지 마세요.
기록에 남은 방향을 기준으로 작업하고, 필요할 때 기존 이미지 확인을 요청합니다.

현재 Godot 모델의 상태:
- 기본 도형을 조합해 만든 초기 3D 모델.
- 공간, 동선, 장비 점유, 조작을 확인하는 용도.
- 최종 A+C 아트 완성본이 아닙니다.
- 최종 캐릭터 리깅, 표정, 고급 애니메이션은 아직 없습니다.

이전 대화에서 생성한 병원·민지 등의 이미지는
기획과 아트 방향 검토용입니다.
그 이미지 자체가 3D 모델이나 실행 가능한 게임 에셋이라는 뜻은 아닙니다.

5. 사용자가 추가한 장기 성장 세계관
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

사용자의 새 아이디어:

“심시티처럼 병원이 커지고 돈이 많아져서 다른 지역에도 병원을 설립하고,
방사선치료시스템 연구소 같은 것도 설립하고,
그래서 치료율도 높이고,
점점 세계로 뻗어가는 세계관이면 재밌을 것 같다.”

이 방향을 프로젝트의 장기 성장 목표로 반영하기로 했습니다.

정리한 성장 단계:
1. 작은 동네 방사선과
2. 지역 거점병원
3. 치료시스템 연구소
4. 여러 지역의 병원
5. 세계적인 병원 네트워크

제안한 핵심 순환:
환자 치료
→ 수입과 평판
→ 병원 증축·직원·연구 투자
→ 더 나은 치료 성과와 운영 능력
→ 새로운 지역 진출

여러 병원이 생겼을 때의 운영 방향:
- 처음에는 직접 접수와 업무 지시로 운영을 배웁니다.
- 이후 직원에게 일상 업무를 맡깁니다.
- 플레이어는 증축, 연구, 인력 배치, 신규 지역 투자에 집중합니다.
- 병원 수가 늘어날수록 접수 버튼을 끝없이 눌러야 하는 구조는 피합니다.

연구소 기능으로 제안한 분야:
- 치료계획 기술.
- 장비 안정성과 운영 효율.
- 직원 교육.
- 새로운 치료 관련 콘텐츠.

지역별 차이로 제안한 요소:
- 환자 수요.
- 인력 확보 조건.
- 병원 설립 조건.
- 운영상의 과제.
- 건물과 주변 환경의 개성.

주의:
위 장기 성장 방향은 사용자 아이디어를 반영한 기획입니다.
여러 병원, 연구소, 세계 지도, 해외 진출은 아직 코드로 구현하지 않았습니다.
구체적인 연구 가격, 지역 이름, 해금 수치, 치료 성과 공식은 확정하지 않았습니다.
게임용 치료 성과 수치를 실제 임상 치료율처럼 표현하지 않습니다.

환경 장애 이후 이 아이디어가 나왔기 때문에,
관련 기획이 기존 프로젝트 파일에 저장됐다고 가정하면 안 됩니다.
이 대화 인계서를 바탕으로 새 문서에 반영해야 합니다.

6. 지역 확장 지도 시안
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

지역 확장 지도 콘셉트 한 장을 만들었습니다.

구성:
- 앞쪽에 작은 동네 병원.
- 중간에 지역 거점병원.
- 별도 건물로 치료 연구소.
- 바다 건너 해외 병원.
- 길과 다리로 연결되는 성장 구조.
- 크림색·청록색, 녹지, 따뜻한 햇빛.
- 작은 병원에서 큰 네트워크로 발전하는 느낌.

시안의 주요 문구:
- 햇살병원
- 우리 병원의 다음 이야기
- 동네 병원
- 지역 거점병원

- 해외 진출

이 새 지도 시안에 대한 별도의 최종 승인까지 받았다고 가정하지 마세요.

7. 마지막으로 실제 완료한 게임 기능

실제 Godot 프로젝트에서 다음 기능을 구현하고 실행했습니다.

A. 병원 내부
- 고정 카메라로 보는 실제 3D 공간.
- 대기실, CT실, 계획실, 치료실.
- 공용 복도와 출입 경로.
- 코드로 생성한 바닥, 벽, 창문, 가구, 장비.
- 단순한 3D 환자와 직원.
- 기본 걷기 동작.
- CT 촬영과 치료 때 환자가 장비 위에 누워 있는 표시.
- 장비 사용 상태에 따른 시각 효과.

B. 환자 운영
- 하루에 환자 네 명이 차례로 방문.
- 환자 선택.
- 접수 지시.
- CT 촬영.
- 직원에게 치료계획 검토 맡기기.
- 치료실로 이동.
- 치료 완료 후 수입 지급.
- 귀가.
- 장비가 차 있으면 대기열에 들어감.

C. 장비 예약과 점유
- CT 장비 한 대.
- 계획 담당 직원 한 명.
- 처음에는 치료실 한 개.
- 장비로 이동하는 동안에도 해당 장비를 예약.
- 같은 장비로 두 환자가 동시에 배정되지 않음.
- 대기열의 순서대로 다음 환자를 안내.

D. 병원 안/밖 전환
- ‘병원 밖’으로 외관을 볼 수 있음.
- 밖을 보는 동안 진료가 일시정지됨.
- 안으로 돌아오면 전환 전 재생 상태를 복원.
- 원래 일시정지였다면 돌아와도 일시정지 유지.

E. 실제 증축
- 첫 환자 치료 완료 후 증축 해금.
- 600만을 지불.
- 구매 확인창 표시.
- 취소하면 비용과 건물에 변화 없음.
- 자금 부족 시 구매 차단.
- 중복 구매와 중복 결제 차단.
- 외관에 치료별관과 연결동 생성.
- 내부에 확장 공간과 두 번째 치료 장비 생성.
- 별관 담당 인물 추가.
- 치료실 용량이 1개에서 2개로 증가.
- 두 환자가 실제로 동시에 치료 가능.
- 진행 중인 환자의 상태를 유지하면서 확장.

F. 다음 날 운영
- 네 환자가 모두 귀가하면 다음 날 시작 가능.
- 다음 날에도 자금과 별관 유지.
- 새로운 환자들이 다시 도착.
- 하루 진행 상태와 장비 예약은 새로 시작.
- 누적 완료 수 유지.
- 진행 중에 다음 날을 중복 시작하지 못함.

G. 저장과 복원
- 로컬 자동 저장.
- 환자 위치, 이동 경로, 업무 상태, 자금, 증축 여부 등을 저장.
- 복원은 일시정지 상태로 시작.
- 손상된 저장은 자동 덮어쓰지 않음.
- 이전 단일 환자 버전 저장의 이전 기능.
- 두 치료실이 사용 중인 상태도 복원.
- 복원 후 치료비가 중복 지급되지 않도록 검증.

아직 Android APK나 iOS IPA는 없습니다.
실기기에서 동작과 성능을 검증한 단계도 아닙니다.

8. 현재 게임 수치와 의미
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

다음 수치는 최종 밸런스가 아니라 운영 검증용 임시 값입니다.

- 초기 자금: 900만
- 환자 한 명 치료 완료 수입: 200만
- 치료별관 증축 비용: 600만
- 하루 환자 수: 4명
- 첫 환자: 하루 시작 시 생성
- 이후 도착 간격: 6초
- 이동 속도: 초당 2.1 공간 단위
- CT 촬영 시간: 5초
- 계획 검토 시간: 5초
- 치료 시간: 30초

첫날 네 명을 치료하고 별관을 한 번 증축했을 때:
900 + 200×4 - 600 = 1100만

치료 수입 지급 시점:
치료가 끝나는 시점입니다.
병원 밖으로 완전히 나간 뒤에 지급하는 것이 아닙니다.

completed():
치료 수입을 지급한 환자의 수를 셉니다.

all_done():
네 환자가 모두 귀가 완료 상태일 때만 true입니다.

이 구분 때문에 완료 수가 4/4로 보이더라도
마지막 환자가 아직 출구로 이동 중일 수 있습니다.
다음 날 시작은 모두 귀가한 뒤 가능합니다.

11. 핵심 코드 구조 — 운영 시뮬레이션
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

godot/scripts/hospital_simulation.gd

형태:
- RefCounted 기반.
- changed 신호.
- 화면 모델과 운영 규칙을 분리.

주요 상수:
- EXPANSION_COST = 600
- VISIT_FEE = 200
- MAX_PATIENTS = 4
- SPEED = 2.1
- DURATIONS:
  ct_scan = 5.0
  planning = 5.0
  treatment = 30.0

주요 상태:
- patients: Array[Dictionary]
- day
- lifetime_completed
- time
- next_arrival
- money
- expanded
- paused
- ct_owner
- planner_owner
- treatment_owners
- max_treating
- serial

치료실 소유자 배열:
증축 전 [-1]
증축 후 [-1, -1]

-1은 빈 장비를 의미합니다.

환자 데이터:
- id
- name
- state
- position: Vector3
- route: 이동할 Vector3 목록
- next_state
- elapsed
- room: 치료실 번호 또는 -1
- paid: 치료비 지급 여부
- queue_order
- history: 통과한 상태 기록

사용한 환자 이름:
김영수, 이정호, 박상철, 최민석.
다음 날에는 이름 배치를 순환시키는 초기 구현입니다.
최종 캐릭터와 환자 콘텐츠로 확정된 것은 아닙니다.

주요 메서드:
- get_patient(id)
- completed()
- all_done()
- count_state(state)
- spawn()
- set_state(patient, value)
- travel(patient, state, points, destination)
- enqueue(patient, state)
- admit(id)
- assign_plan(id)
- first_queued(state)
- dispatch()
- tick(delta)
- expansion_reason()
- purchase_expansion()
- start_next_day()
- snapshot()
- restore(data)
- migrate_v1(data)

운영 규칙:
- admit()은 waiting 상태이고 일시정지가 아닐 때만 성공.
- assign_plan()은 plan_ready 상태이고 일시정지가 아닐 때만 성공.
- 장비가 비면 대기 순서가 가장 빠른 환자를 배정.
- 이동을 시작할 때 장비를 예약.
- 도착해야 실제 검사나 치료가 시작.
- paused이면 환자 이동과 업무 시간이 멈춤.
- 치료 완료 시 paid가 false일 때만 수입 지급.
- 완료 후 추가 tick으로 돈이 중복 증가하지 않음.

13. 공간과 동선 구현 기록
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

좌표 기준:
- 바닥에서의 환자 시뮬레이션 위치는 y=0.
- 화면에 보이는 캐릭터에는 작은 높이 오프셋을 적용.
- x≈0 부근에 공용 복도.
- 왼쪽에 대기실과 CT실.
- 오른쪽에 계획실과 기존 치료실.
- 오른쪽으로 별관 확장.

대표 위치:
- 입구: (0, 0, 6.6)
- CT 환자 위치: (-5, 0, -1.8)
- 본관 치료 환자 위치: (5, 0, 4)
- 별관 치료 환자 위치: (11, 0, 4)

대기 위치:
x = -4.8 + ((id - 1) % 2) × 1.2
z = 2.8 + floor((id - 1) / 2) × 1.4

입장 경로:
(0, 0, 6.6)
→ (0, 0, 3)
→ (-2.5, 0, 3)
→ 환자별 대기 위치

접수 후 CT 이동:
대기 위치
→ (-2.5, 0, 3)
→ (0, 0, 3)
→ (0, 0, -2.8)
→ (-2.5, 0, -2.8)
→ (-5, 0, -1.8)

이 경로는 대기실 쪽 벽을 가로지르던 문제를 수정한 결과입니다.

CT 이후:
왼쪽 출입구 → 중앙 복도 → 오른쪽 계획실 출입구 → 환자별 계획 대기 위치.

본관 치료실:
계획실 출입구 → 중앙 복도 → 남쪽 치료실 출입구 → 기존 장비.

별관 치료실:
기존 치료실 쪽 통로에서 z≈5.2 경로를 따라 별관 장비로 이동.

주의:
전체 경로가 최종 NavMesh 기반 자유 이동은 아닙니다.
직접 지정한 waypoint 경로를 따라 움직이는 초기 구현입니다.
새 공간이나 장비를 추가할 때는 벽·가구·환자 겹침을 다시 확인해야 합니다.
특히 별관을 오가는 경로와 귀가 경로도 실제 장면에서 확인하세요.
검증 기록만 보고 모든 충돌과 가림 문제가 해결됐다고 가정하지 마세요.

- 환경 ID만으로는 AI 상담이 원래 task를 식별할 수 없다고 답함.
- 저장된 VM 상태가 마지막 시작/재개 후 최대 7일까지 복구 가능할 수 있다고 설명.

주의:
7일이라는 문구는 지원 AI가 전달한 설명입니다.
이 프로젝트 파일의 실제 보존 기간과 복구 가능성을 확인받은 것은 아닙니다.

사용자 측에서 겪은 추가 문제:
- 공유창이 ‘미리보기 불러오는 중…’에서 멈춤.
- ‘링크 복사’가 비활성화됨.
- chatgpt.com/local/... 주소는 지원 측에서 Cloud task 링크로 인정하지 않음.
- 환경 목록에 Game이 두 개 있다는 대화가 있었음.
- 지원 측이 안내한 Continue/Reopen 메뉴가 사용자 화면에는 없었음.
- 사용자가 여러 번 없다고 말했는데도 비슷한 메뉴와 캡처 요청이 반복되어 크게 불편을 겪음.

새 채팅에서는:
- 화면에서 확인하지 않은 메뉴가 있다고 단정하지 마세요.
- Continue/Reopen, Work in > Cloud 등이 실제 있는지 모르면 확정적으로 안내하지 마세요.
- 이미 없는 것으로 확인된 버튼을 계속 찾게 하지 마세요.
- 같은 공유창 열기, 같은 앱 재실행, 같은 오류 명령을 근거 없이 반복하지 마세요.
- 새 task를 만들면 원래 미커밋 파일이 자동으로 돌아온다고 말하지 마세요.
- 환경 설정 선택과 원래 작업 공간 복구를 혼동하지 마세요.
- 공개 채팅 공유 링크와 실제 Cloud task 식별자를 혼동하지 마세요.

사람 지원 담당자로 에스컬레이션하는 선택 화면까지 나왔습니다.
답변에 며칠 걸릴 수 있다는 안내가 있었습니다.
실제 접수 완료 및 접수번호는 이 기록에서 확인되지 않았습니다.

사용자는 지원 답변만 기다리며 개발이 멈추는 것을 원하지 않습니다.
그래서 다른 채팅에서 이어가기 위해 이 상세 인계서를 요청했습니다.
